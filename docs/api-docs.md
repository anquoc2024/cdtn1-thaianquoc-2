# API Documentation — Smart CRM (Mekong Mobile), flow L2

Warranty request intake and classification · Track SE · Tag `v1.0`
Author: Thái An Quốc (2374802012635) · Repository: https://github.com/anquoc2024/cdtn1-thaianquoc-2

This document describes **every endpoint that exists** in the JSON API (`src/config/routes.rb`, `namespace :api`):
21 endpoints in 6 groups. Each endpoint has seven parts — method and path, description, authentication,
parameters, success response, error codes, limits — and a **real** example. All examples are copied from
`docs/api-examples.md`, generated by `docs/scripts/goi-api-docker.sh` against the Docker stack on 2026-11-10
(46 requests, all returned the expected status). "Example #n" refers to request *n* in that file.
Long lists are shortened with `…`; tokens are replaced by `<token>`.

## 0. Common rules

### 0.1 Base URL, format

- Base URL: `http://localhost:3000/api` (the port follows `APP_PORT`, see `docs/deployment-guide.md`).
- Requests and responses are JSON (UTF-8). Send bodies with `Content-Type: application/json`.
- Times are ISO 8601 in the server time zone, e.g. `2026-11-10T21:50:52+07:00`; dates are `YYYY-MM-DD`.
- JSON field names in responses are partly Vietnamese; see the glossary in 0.6.

### 0.2 Authentication

Every endpoint except `POST /api/session` and `GET /api/health` needs an authenticated user. Two ways:

1. **Token (curl, Postman):** get a token from `POST /api/session`, then send
   `Authorization: Bearer <token>` with every request.
2. **Browser session (the app's own JavaScript):** the signed `session_id` cookie of the web login **plus** the header
   `X-Requested-With: XMLHttpRequest`. Without that header the cookie is ignored (CSRF protection).

A token stays valid until `DELETE /api/session`, which replaces it (Example #45, #46). Tokens have no expiry date
(known limitation, `docs/checklist-bao-mat.md` item 4).

### 0.3 Roles and permissions

| Permission | Receptionist (`receptionist`) | Service centre manager (`manager`) | Used by |
|---|---|---|---|
| `lookup_customers` | ✓ | ✓ | `GET /customers`, `GET /customers/{id}` |
| `manage_customers` | ✓ | — | `POST`, `PATCH`, `DELETE /customers` |
| `view_requests` | ✓ | ✓ | `GET /warranty_requests/{id}`, `GET /issue_categories`, `GET /priorities` |
| `view_request_list` | ✓ | ✓ | `GET /warranty_requests`, `GET /stats` |
| `create_requests` | ✓ | ✓ | `POST /warranty_requests` |

A signed-in user without the permission gets `403 KHONG_CO_QUYEN` (Example #11, #35, #42).

### 0.4 Error format and codes

Every error has the same shape; `chi_tiet` appears only when there are details:

```json
{ "error": "MA_LOI", "message": "Human-readable message (Vietnamese)", "chi_tiet": { "cac_truong": [ { "truong": "phone", "ly_do": "…" } ] } }
```

| HTTP | `error` | Meaning |
|---|---|---|
| 400 | `DU_LIEU_KHONG_HOP_LE` | Invalid field values (`chi_tiet.cac_truong` lists them), missing required parameter, or malformed JSON body |
| 400 | `TRANG_THAI_KHONG_HOP_LE` | `status` is not one of `received`, `in_progress`, `completed`, `cancelled` |
| 400 | `THIEU_LY_DO_HUY` | Cancelling without a `note` |
| 401 | `CHUA_XAC_THUC` | Missing, wrong or revoked token |
| 401 | `SAI_THONG_TIN_DANG_NHAP` | Wrong email or password at sign-in |
| 403 | `KHONG_CO_QUYEN` | The role does not have the permission (0.3) |
| 404 | `KHONG_TIM_THAY` | No record with this id |
| 404 | `KHACH_HANG_KHONG_TON_TAI` | `customer_id` of a new warranty request does not exist (BR01) |
| 409 | `TRUNG_DU_LIEU` | Unique value already used (customer phone, category name) |
| 409 | `DANG_DUOC_SU_DUNG` | Record still referenced (customer with devices – BR13, category with requests – BR14) |
| 409 | `SERIAL_THUOC_KHACH_KHAC` | Serial / IMEI already registered to another customer (NFR04) |
| 409 | `YEU_CAU_DA_DONG` | Status change on a completed or cancelled request |
| 409 | `KHONG_XOA_DUOC` | The database refused to delete the warranty request |
| 422 | `CHUYEN_TRANG_THAI_KHONG_HOP_LE` | Transition not allowed (e.g. `received` → `completed`, BR08) |
| 429 | `QUA_NHIEU_LAN_THU` | More than 10 sign-in attempts in 3 minutes |
| 500 | `LOI_HE_THONG` | Unexpected error; `chi_tiet.ma_tra_cuu` is the request id to find the log line |
| 503 | `CSDL_KHONG_KHA_DUNG` | Database unreachable; includes `chi_tiet.ma_tra_cuu` and header `Retry-After: 30` |

Error responses never contain stack traces, SQL or connection strings (checked in `docs/checklist-bao-mat.md` item 5).

### 0.5 Status workflow of a warranty request

`received` (Mới tiếp nhận) → `in_progress` (Đang xử lý) → `completed` (Hoàn tất); `received` or `in_progress` →
`cancelled` (Đã hủy, needs a reason). `completed` and `cancelled` are closed. "Overdue" (Quá hạn) is not stored: it is
shown when an open request is past `due_at`. `due_at` = `created_at` + SLA hours of the priority (BR06).

### 0.6 Glossary of Vietnamese field names

| Field | Meaning | Field | Meaning |
|---|---|---|---|
| `trang` | current page | `chi_tiet` | details |
| `so_trang` | number of pages | `cac_truong` / `truong` / `ly_do` | fields / field / reason |
| `tong_so` | total records | `ma_tra_cuu` | lookup code (= request id in the server log) |
| `moi_trang` | records per page | `so_yeu_cau` | number of warranty requests of the customer |
| `tim_theo` | how `q` was matched: `phone`, `code`, `name` | `yeu_cau_gan_nhat` | time of the customer's latest request |
| `moc` (`ten`, `so`) | comparison baseline (label, value) | `ty_le` | percentage |

## 1. Session and health

### 1.1 `POST /api/session` — sign in

| Part | Content |
|---|---|
| 1. Method & path | `POST /api/session` |
| 2. Description | Checks email and password and returns the user's API token, role and permission list. |
| 3. Authentication | None. |
| 4. Parameters | Body: `email_address` (string, required), `password` (string, required). |
| 5. Success | `200` — `data.token`, `data.token_type` (`"Bearer"`), `data.user` {`id`, `full_name`, `email_address`, `role`, `role_label`, `permissions[]`}. |

Example #1:
```bash
curl -X POST -H 'Content-Type: application/json' -d '{"email_address":"quoc@mekong.vn","password":"Mekong@2026"}' 'http://localhost:3000/api/session'
```
```json
HTTP 200
{ "data": { "token": "<token>", "token_type": "Bearer",
    "user": { "id": 1, "full_name": "Thái An Quốc", "email_address": "quoc@mekong.vn", "role": "receptionist",
              "role_label": "Nhân viên tiếp nhận",
              "permissions": ["lookup_customers", "create_requests", "change_status", "view_requests", "view_request_list",

```

## 2. Customers

Customer object: `id`, `code` (`KH-000001`… for customers created in the app; imported sample customers use codes from `KH-100000` up), `name`, `phone`,
`email`, `address`, `created_at`, `updated_at`. `GET` responses add `so_yeu_cau` and `yeu_cau_gan_nhat`.

### 2.1 `GET /api/customers` — list or search customers

| Part | Content |
|---|---|
| 1. Method & path | `GET /api/customers` |
| 2. Description | Without `q`: all customers, newest first, paginated. With `q`: search by phone (starts with 0, 10 digits, spaces allowed), customer code (`KH-000245`, `kh245`, `245`) or name (accents and case ignored) — UC01. |
| 3. Authentication | Bearer token · `lookup_customers` (receptionist, manager). |
| 4. Parameters | Query: `q` (optional), `page` (optional, default 1, only without `q`). |
| 5. Success | `200` — `data[]` customers, `meta` {`trang`, `so_trang`, `tong_so`, `moi_trang`} (+ `tim_theo` when `q` is given). Nothing found → `200` with `data: []` (UC08). |
| 6. Errors | `400 DU_LIEU_KHONG_HOP_LE` — phone not 10 digits, or name shorter than 2 characters (Example #6) · `401` · `403`. |
| 7. Limits | 20 per page; a search returns at most 20 customers. Queries are parameterised (`' OR '1'='1` returns 0 rows, TC-16). |

Example #5:
```bash
curl -G -H 'Authorization: Bearer <token>' --data-urlencode 'q=0901234567' 'http://localhost:3000/api/customers'
```


## 5. Warranty requests

Summary object (list): `id`, `code` (`BH-YYYY-NNNNNN`), `status`, `status_label`, `overdue`, `priority`, `sla_hours`,
`issue_category`, `customer_code`, `customer_name`, `customer_phone`, `device`, `created_at`, `due_at`, `closed_at`.
Detail object adds `issue_description`, `device_detail` {`device_type`, `brand`, `model`, `serial_number`,
`purchase_date`, `warranty_card_number`}, `allowed_next_statuses[]` and `status_logs[]` {`from`, `to`, `note`,
`changed_by`, `at`}.

### 5.1 `GET /api/warranty_requests` — list requests

| Part | Content |
|---|---|
| 1. Method & path | `GET /api/warranty_requests` |
| 2. Description | Filters, sorts and paginates warranty requests (UC07). |
| 3. Authentication | Bearer token · `view_request_list` (receptionist, manager). |

### 5.3 `POST /api/warranty_requests` — create a request

| Part | Content |
|---|---|
| 1. Method & path | `POST /api/warranty_requests` |
| 2. Description | Creates a warranty request for an existing customer (UC06). Reuses the device when the serial already belongs to this customer, otherwise registers it. The server generates `code`, sets status `received` and `due_at` = now + SLA hours. |
| 3. Authentication | Bearer token · `create_requests` (receptionist, manager). The token owner is recorded as creator. |
| 4. Parameters | Body: `customer_id` (required), `device_type`, `brand`, `model`, `serial_number` (≤ 50), `purchase_date` (`YYYY-MM-DD`), `issue_description` (≤ 1000), `issue_category_id`, `priority_id` — all required; `warranty_card_number` (optional, ≤ 50); `customer_name` (optional, updates the customer's name, ≤ 100). |
| 5. Success | `201 Created`, header `Location: /api/warranty_requests/{id}`, `data` detail object. |
| 6. Errors | `400 DU_LIEU_KHONG_HOP_LE` with field list (Example #29) or malformed JSON (Example #32) · `404 KHACH_HANG_KHONG_TON_TAI` (Example #30) · `409 SERIAL_THUOC_KHACH_KHAC` (Example #31) · `401` · `403`. |
| 7. Limits | Request and device are saved in one transaction; on any error nothing is created. |

### 5.4 `PATCH /api/warranty_requests/{id}` — update a request

| Part | Content |
|---|---|
| 1. Method & path | `PATCH /api/warranty_requests/{id}` |
| 2. Description | Changes only the fields that are sent (TD-29). Changing the priority recalculates `due_at` from `created_at`. The change is written to `status_logs` ("Sửa thông tin: …"). |
| 3. Authentication | Bearer token · `edit_requests` (receptionist only). |
| 4. Parameters | Path: `id`. Body (any of): `device_type`, `brand`, `model`, `purchase_date`, `warranty_card_number`, `issue_description`, `issue_category_id`, `priority_id` — same rules as 5.3. |
| 5. Success | `200` — `data` detail object. |
| 6. Errors | `400 DU_LIEU_KHONG_HOP_LE` (Example #34) · `403 KHONG_CO_QUYEN` for managers (Example #35) · `404` · `401`. |
| 7. Limits | `serial_number`, `customer_id` and `status` cannot be changed here (status: 5.6). |

### 5.5 `DELETE /api/warranty_requests/{id}` — delete a request

| Part | Content |
|---|---|
| 1. Method & path | `DELETE /api/warranty_requests/{id}` |
| 2. Description | Deletes the request and its status history (TD-29); the device and the customer are kept. The deletion is logged with the request code and the user id. |
| 3. Authentication | Bearer token · `delete_requests` (receptionist only). |
| 4. Parameters | Path: `id`. |
| 5. Success | `204 No Content` (Example #43). |
| 6. Errors | `404 KHONG_TIM_THAY` (Example #44) · `403 KHONG_CO_QUYEN` (Example #42) · `409 KHONG_XOA_DUOC` · `401`. |
| 7. Limits | Allowed in every status; cannot be undone. |

### 5.6 `PATCH /api/warranty_requests/{id}/status` — change status

| Part | Content |
|---|---|
| 1. Method & path | `PATCH /api/warranty_requests/{id}/status` |
| 2. Description | Moves the request along the workflow in 0.5 and writes a history line, in one transaction with a row lock. Closing (`completed` / `cancelled`) sets `closed_at`. |
| 3. Authentication | Bearer token · `change_status` (receptionist only). |
| 4. Parameters | Path: `id`. Body: `status` (required: `in_progress`, `completed`, `cancelled`), `note` (required when `status` is `cancelled`, optional otherwise). |
| 5. Success | `200` — `data` detail object with new `status`, `allowed_next_statuses` and history. |
| 6. Errors | `400 DU_LIEU_KHONG_HOP_LE` missing `status` (Example #38) · `400 TRANG_THAI_KHONG_HOP_LE` unknown value · `400 THIEU_LY_DO_HUY` (Example #39) · `422 CHUYEN_TRANG_THAI_KHONG_HOP_LE` (Example #36) · `409 YEU_CAU_DA_DONG` (Example #41) · `404` · `403` · `401`. |
| 7. Limits | Steps cannot be skipped (BR08); closed requests cannot be reopened. |

## 6. How to reproduce the examples

```bash
docker compose up -d                      # wait until db and app are healthy
bash docs/scripts/goi-api-docker.sh       # sends the 46 requests, rewrites docs/api-examples.md
```

The script creates, edits and deletes a few test records; `docker compose down -v && docker compose up -d` restores
the sample data. Automated API tests: `src/test/integration/api_*_test.rb` (part of `bin/rails test`).
